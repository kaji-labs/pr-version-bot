# Suggestions — PR Version Bot

_Generated by code quality / security scan. These are non-urgent improvements worth building, not bugs._

---

## Security / Hardening

### S-001 — Block IPv6 private ranges in SSRF guard (`notify.ts`)

The current SSRF block list in `requireHttps` covers IPv4 private ranges and `::1` (loopback) but does not cover the full IPv6 private address space: `fc00::/7` (unique local, `fc00::` through `fdff::`) and `fe80::/10` (link-local). A user could configure a webhook URL like `https://fd12:3456:789a::1/exfil` and bypass the guard. Add regex patterns for `^fc[0-9a-f]{2}:` and `^fe[89ab][0-9a-f]:` to the `SSRF_BLOCKED_PATTERNS` array. Low probability in practice (GitHub Actions runners are heavily firewalled) but worth closing for completeness before public Marketplace listing.

### S-002 — Redact webhook URLs from `core.warning` error messages (`notify.ts`)

When `sendSlackNotification` or `sendDiscordNotification` log a failure (e.g. "Slack notification failed with status 403"), the webhook URL itself is not logged — good. However, if the underlying `https.request` rejects, the error object propagated upward could include the full URL in its `.message` field depending on the Node.js version. Consider wrapping the `post()` rejection to strip the URL before it reaches `core.setFailed`. Apply the same pattern used in `pushWithProtectionCheck` (extract message, wrap with a sanitised message).

### S-003 — Validate `tag-prefix` against an allowlist (`config.ts`)

`tagPrefix` is user-controlled and is interpolated directly into git tag names and README content without validation. A prefix like `../../refs/tags/` could produce a malformed ref. Add a validation step that rejects any `tagPrefix` not matching `/^[a-zA-Z0-9._-]*$/` with a clear error message.

### S-004 — Validate `commit-message-template` length (`config.ts`)

There is no length cap on `commitMessageTemplate`. An extremely long template would produce a commit message that is technically valid but can confuse tooling and log viewers. Cap at 200 characters with a clear error.

## Correctness / Robustness

### S-005 — `detectBumpFromPrBody` substring match is order-dependent and can produce false positives (`pr-template.ts`)

The PR body scanner uses `text.includes(labelValue)` to match a checkbox line against configured label values. If a label value is a substring of another (e.g. `release:patch` and `release:patch-hotfix`), whichever appears first in `Object.entries(labelToType)` wins, potentially producing the wrong result. Replace substring matching with whole-word / exact equality matching after stripping markdown syntax from the checkbox text.

### S-006 — `bumpPrerelease` does not validate `channel` against the semver channel in the existing pre-release tag (`version.ts`)

`bumpPrerelease('1.0.0-alpha.2', 'beta')` returns `1.0.1-beta.1` — it resets the patch counter and starts at 1. This is arguably correct, but it silently changes the patch number which can surprise users who expect `1.0.0-beta.1`. Consider emitting a `core.warning` (from the call site in `index.ts`) when the channel changes, so the version jump is visible in the logs.

### S-007 — `commitRelease` does not verify that files actually changed before staging (`git.ts`)

`commitRelease` calls `git add` for every file in `filesToCommit` and then immediately `git commit`. If any file was unmodified (e.g. `writeVersion` wrote the same content), `git commit` will still succeed because other files changed. But in a hypothetical code path where all files are unchanged, `git commit` would fail with "nothing to commit". A `git diff --staged --quiet` guard (similar to `build-dist.yml`) before `git commit` would make this more robust.

### S-008 — Monorepo `versionFile` is not validated for path traversal (`monorepo.ts` / `config.ts`)

`validateNoPaths` correctly rejects package paths that traverse outside the workspace. However, the `versionFile` parameter passed to `resolvePackagePaths` is the user-configured `config.versionFile` (e.g. `../../.env`). A malicious config could set `versionFile: ../../some/sensitive/file` and have `resolvePackagePaths` construct a path that escapes the workspace. Apply `validateNoPaths([versionFile])` (or an equivalent single-path check) before the join in `resolvePackagePaths`.

### S-009 — `sanitiseReleaseBranch` preserves `/` which can produce double-slash branches (`release-pr.ts`)

The function prefixes `release/` and then calls `tag.replace(/[^a-zA-Z0-9/.-]/g, '-')`. If `tagPrefix` is empty, or if the tag itself contains a slash (unusual but possible with a custom prefix like `releases/`), the result is `release/releases/v1.0.0`. Git accepts this, but it creates a confusing nested ref path. Remove `/` from the allowed characters in the sanitiser — slashes in a tag should map to `-`. Updated regex: `[^a-zA-Z0-9.-]`.

## Performance / DX

### S-010 — Cache the Octokit client to avoid double instantiation (`index.ts`)

`github.getOctokit(token)` is called up to twice in `run()`: once in the conventional commits block and once in `createRelease`. Each call creates a new Octokit instance. Instantiate once and pass to the functions that need it. Minor allocation saving, but also makes token lifetime explicit.

### S-011 — Surface `skipped` output even when action exits early (`index.ts`)

When the action exits because `!pr?.merged`, it returns without setting any outputs. Callers that branch on `steps.version-bot.outputs.skipped` would see an empty string rather than `'true'`. Set `core.setOutput('skipped', 'true')` before every early return so downstream steps can always read this output reliably.

### S-012 — Allow configuring the release PR base branch separately from `target-branch` (`config.ts` / `release-pr.ts`)

Currently `use-release-pr` opens a PR targeting `target-branch` (default: `main`). If a user wants release commits to go to a `develop` branch but their repo default branch is `main`, there is no way to separate these. Add an optional `release-pr-base` input that defaults to `target-branch` but can be overridden.

## Observability

### S-013 — Emit a GitHub Actions Step Summary (`index.ts`)

Use `core.summary` (available since `@actions/core` 1.9) to write a structured summary table to the workflow run page. Include: previous version, new version, bump type, tag created, changelog entry, and a link to the GitHub Release. This gives users a glanceable record of what the action did without needing to read log lines.

### S-014 — Log file paths written during the release (`index.ts`)

The action silently writes to `VERSION.md`, `CHANGELOG.md`, optional `package.json`, badge, and README without logging which files were modified. Adding a `core.info(\`Files staged: ${filesToCommit.join(', ')}\`)`line before`commitRelease` would make dry-run output more useful and help debug unexpected diff contents.

### S-015 — Add `release-notes-url` output (`github-release.ts` / `index.ts`)

`createRelease` returns the full Octokit response which includes `data.html_url` (the URL of the GitHub Release page). Expose this as a `release-url` action output so downstream jobs can post it to PRs, Slack, etc., without needing to reconstruct the URL.

## Features

### S-016 — Support per-package changelog files in monorepo mode (`index.ts` / `changelog.ts`)

In monorepo mode, each package gets its own changelog prepended at `{pkgDir}/CHANGELOG.md`. The filename is derived by stripping the directory from `config.changelogFile`. If a user sets `changelog-file: docs/HISTORY.md`, the per-package file becomes `{pkgDir}/HISTORY.md` — this works, but is not documented. Make the behaviour explicit in `action.yml` and consider adding a `per-package-changelog-file` input to allow independent control.

### S-017 — Prerelease channel promotion guard (`version.ts` / `index.ts`)

`bumpPrerelease('1.0.0-beta.2', 'alpha')` happily produces `1.0.1-alpha.1`, which moves backward through channels on a new patch. There is no validation that channel ordering is respected (alpha → beta → rc → stable). Add an optional `enforce-channel-order: true` input that throws if a PR requests a lower-precedence channel than the current one.

### S-018 — Dry-run should output the computed changelog entry (`index.ts`)

In dry-run mode, the action reports the next version and tag but does not show what the changelog entry would look like. Calling `buildEntry(...)` and logging it (without writing) would make dry-run much more useful for validation in PRs.

### S-019 — Support multiple notification channels per webhook type (`config.ts` / `notify.ts`)

Currently only one Slack and one Discord URL can be configured. Teams often want to notify multiple channels (e.g. `#releases` and `#team-alerts`). Accept comma-separated URLs for `slack-webhook-url` and `discord-webhook-url` and send to all of them, collecting failures as warnings rather than halting on the first.

### S-020 — Configurable `prerelease: true` on GitHub Releases for pre-release channels (`github-release.ts`)

`createRelease` always passes `prerelease: false`. When the bump type is `alpha`, `beta`, or `rc`, the GitHub Release should be marked as a pre-release automatically (`prerelease: true`). This makes the Releases page cleaner and prevents Shields.io `latest` badges from picking up pre-release versions. Add a simple `bump === 'alpha' || bump === 'beta' || bump === 'rc'` check.

### S-025 — Auto-update all version refs in README on release (`readme.ts` / `index.ts`)

The `## Install` section is kept current via the VERSIONBOT markers and `update-readme: true`. However, version refs embedded in other README sections — such as the `## Example workflow` block — still show a static, manually-maintained version string (currently `@v0.9.1`). Any new release makes these stale immediately.

Extend `applyReadmeUpdate` (or add a companion function `updateVersionRefs`) that does a global regex replacement of the previous action ref in the README file. After each release, replace all occurrences of `kaji-labs/pr-version-bot@{previousTag}` with `kaji-labs/pr-version-bot@{newTag}` in the file before committing. The replacement is safe because the old version string is specific enough to avoid false matches. This should be opt-in via the existing `update-readme` flag — no new input needed. The function should also handle pre-release tags (`@v1.0.0-alpha.1`), replacing them with the new tag whether that tag is stable or another pre-release.

**Implementation sketch:**

```typescript
function updateVersionRefs(content: string, previousTag: string, newTag: string): string {
  const escaped = previousTag.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
  return content.replace(new RegExp(escaped, 'g'), newTag);
}
```

Call in `applyReadmeUpdate` after the marker block replacement, before writing the file.

### S-026 — Automatically mark GitHub Releases as pre-release and set the `latest` flag correctly (`github-release.ts`)

Currently all GitHub Releases are created with `prerelease: false` and `make_latest: 'true'` (GitHub default). When a release is for an `alpha`, `beta`, or `rc` channel, this causes two problems: (1) the release incorrectly appears as the "Latest" release on the repo homepage, displacing the last stable version; (2) the GitHub release badge (`img.shields.io/github/v/release/...`) picks up the pre-release version as if it were stable.

Fix: pass `prerelease: bump === 'alpha' || bump === 'beta' || bump === 'rc'` and `make_latest: isPrerelease ? 'false' : 'true'` to `octokit.rest.repos.createRelease`. This keeps the last stable release pinned as "Latest" on the repo page while pre-release versions appear separately under "Releases". The pre-release channel label (`release:alpha/beta/rc`) is already available at the call site in `index.ts`.

## Testing

### S-021 — Integration / smoke test using `act` in CI

The CI pipeline runs unit tests (Vitest) but never exercises the full `run()` function with a mocked GitHub context and real filesystem writes. Adding a test that calls `run()` with a fixture `github.context.payload` and asserts the correct files are written and `core.setOutput` calls are made would catch regressions that unit tests on individual modules miss.

### S-022 — Test `mergeConfig` with all invalid `defaultBump` values

Now that `validateBumpType` is in place, there are no unit tests covering the error path. Add a Vitest test that asserts `mergeConfig` throws with a descriptive message when `default-bump` is set to an invalid value like `"PATCH"` or `"hotfix"`.

### S-023 — Test `requireHttps` SSRF block list exhaustively (`notify.ts`)

The new SSRF block list covers several private ranges but is not tested. Add a Vitest test parameterised over: `https://localhost/`, `https://127.0.0.1/`, `https://169.254.169.254/latest/meta-data/`, `https://10.0.0.1/`, `https://172.16.0.1/`, `https://192.168.1.1/`, `https://[::1]/`, and a valid public URL (`https://hooks.slack.com/`) to verify each is blocked or allowed correctly.

### S-024 — Test `applyReadmeUpdate` when README file does not exist (`readme.ts`)

Now that `applyReadmeUpdate` returns `false` instead of crashing when the README is missing, add a unit test that verifies the function returns `false` without throwing when called with a non-existent file path.
